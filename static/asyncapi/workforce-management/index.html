  • Apache 2.0

  • Workforce Management — claudioed

Domain-event catalog for Workforce Management, a Supporting bounded context in the WES (Warehouse Execution Systems) subdomain. It owns "who is on shift, on which process path, at what rate; direct vs indirect hours" — the shift-start planning horizon (a human commits a split of headcount across paths) plus intra-shift assignment tracking (moving associates between paths as backlogs deviate). It stops at the path boundary: it never links an associate to a specific task, and it never decides a rebalance — it makes the labor picture legible and enforces its invariants.

Three aggregates raise the events documented here:

  • AssociateShift (package internal/domain/associate) — roster entry: who is on, their certifications, their break state, their logged hours. Raises AssociateShiftStarted, AssociateCertified, AssociateBreakStarted, AssociateBreakEnded, AssociateShiftEnded.
  • ShiftPlan (package internal/domain/shiftplan) — the committed split of headcount across paths for one building's shift, made of PathPlan lines. Raises ShiftPlanProposed, ShiftPlanCommitted and the staffing-gap flag PathUnderstaffed.
  • LaborAssignment (package internal/domain/assignment) — one associate on one path for an interval, with exactly one ACTIVE assignment per associate at a time. Raises LaborAssigned and LaborReassigned.

Envelope. Every message on this channel is a CloudEvents 1.0 structured-mode JSON envelope, content type application/cloudevents+json. The CloudEvents context attributes (specversion, id, source, type, subject, time, datacontenttype) sit at the top level and the bounded context's own payload sits under data.

Type naming convention. The CloudEvents type attribute is reverse-DNS dotted and follows the exact shape com.warehouse.<subdomain>.<bounded-context>.<entity>.<EventName>, all lowercase except the final PascalCase event name. For this context the subdomain is wes and the bounded context is workforce-management, so for example a committed shift plan is published as com.warehouse.wes.workforce-management.shiftplan.ShiftPlanCommitted. The entity segment is the aggregate that raises the event — associate, shiftplan or assignment. PathUnderstaffed uses shiftplan, since the gap is measured against a committed ShiftPlan's planned heads.

Full catalog vs actually published. This document is the complete reference catalog of the bounded context's domain events, which is deliberately broader than what leaves the process today. As of this version the outbound Kafka adapter (internal/adapters/outbound/kafka/publisher.go) forwards only ShiftPlanCommitted; every other event in this catalog is raised and consumed in-process and is documented here for completeness and for forward compatibility with downstream contexts. Each message below states its publication status explicitly in its description.

Operations

  • SUB warehouse.workforce.events

    The single outbound topic for this bounded context, matching the Topic constant in internal/adapters/outbound/kafka/publisher.go (warehouse.workforce.events). Messages are CloudEvents 1.0 structured-mode JSON. Consumers must tolerate unknown type values: the catalog on this channel is expected to grow as more of the in-process events below are wired to the publisher.

    Consume Workforce Management domain events.

    Subscribe to the Workforce Management domain-event stream. Every message is a CloudEvents 1.0 structured-mode JSON envelope; route on the type context attribute, which follows com.warehouse.wes.workforce-management.<entity>.<EventName>.

    Only ShiftPlanCommitted is published to this topic today, and it is fanned out into one message per PathPlan line of the committed plan. The remaining messages listed here are part of the domain-event catalog but are in-process only at this version — see each message's description.

    • #0Shift plan committed

      A human committed a headcount split across process paths for a building's shift.

      • application/cloudevents+json

      Raised by the ShiftPlan aggregate when a human commits the split of headcount across process paths for one building's shift. The commit is validated in the domain: plannedHeads(path) must not exceed installedStations(path), and planned hours must fit the shift's max hours.

      Published to Kafka today. This is the only domain event currently wired to the outbound Kafka adapter. The adapter loads the committed plan through the ShiftPlanRepo and fans the single domain event out into one Kafka message per PathPlan line — a plan committed with three path lines produces three messages on warehouse.workforce.events, each carrying that one line's path_id, planned_heads, planned_rate and planned_hours alongside the plan's building_id and shift_id. Consumers must therefore expect N messages per commit, not one, and must not assume a message carries the whole plan.

      allOf

      CloudEvents envelope for one PathPlan line of a committed ShiftPlan. The data fields mirror exactly what the Kafka publisher emits per line.

      A path's active assignments fall short of its committed planned heads.

      • application/cloudevents+json

      Raised when the staffing-gap read model finds that a path's active LaborAssignment count is below the plannedHeads committed for it on the current ShiftPlan. This is a flag, not a decision: this bounded context surfaces the gap and never moves anyone in response. Rebalancing is a human call, recorded back here as a new assignment.

      Not yet wired to the outbound Kafka adapter — documented here as part of the domain-event catalog, in-process only today.

      CloudEvents envelope for the staffing-gap flag on a single path.

      An associate was placed on a process path for an interval.

      • application/cloudevents+json

      Raised by the LaborAssignment aggregate when an associate is assigned to a process path. The domain enforces two hard invariants before this event exists: the associate holds the path's required certification, and the associate has no other ACTIVE assignment (no double-booking across paths).

      Note the path boundary: this places an associate on a path, never on a specific task. Dispatching individual tasks belongs to Fulfillment Execution.

      Not yet wired to the outbound Kafka adapter — documented here as part of the domain-event catalog, in-process only today.
